# 面向全国一卷高中生的个性化编程学习与教学辅助多 Agent 系统需求规格

## 1. 项目定位

### 1.1 服务对象

系统服务对象限定为中国普通高中学生，主要面向采用全国一卷能力导向进行学习和备考的学生。

本文中的“全国一卷”按新课程标准强调的能力导向进行设计，不绑定具体省份名单，重点考虑以下高中生能力基础：

* 阅读理解与信息提取；
* 数学抽象与逻辑推理；
* 问题建模与步骤表达；
* 数据分析与规律发现；
* 规范书写与结果验证；
* 跨学科知识迁移；
* 高考学习时间与心理负荷约束。

系统不将学生默认视为准程序员，也不要求学生过早按照企业岗位标准接受训练。系统首先服务于：

1. 编程启蒙与计算思维培养；
2. 信息技术和人工智能素养提升；
3. 高校计算机类专业认知；
4. 综合素质评价项目积累；
5. 强基计划、综合评价或高校专业面试准备；
6. 有基础学生的项目、算法和工程能力拔高；
7. 教师开展分层教学、项目式教学和过程性评价。

### 1.2 核心场景

系统覆盖四类核心学习场景：

1. **专业与职业方向成长**
   帮助学生了解计算机科学、软件工程、人工智能、数据科学、网络安全等高校专业及其对应职业方向，评估当前基础并生成成长路线。

2. **项目实训**
   将适合高中生的真实问题拆解为阶梯式项目任务，例如校园数据分析、学习工具、科学实验数据处理、简单网站、人工智能应用等。

3. **代码与技能练习**
   对 Python、C++、JavaScript 等代码进行静态检测、错误定位、分步提示、最佳实践讲解和变式练习生成。

4. **高校与专业面试准备**
   面向强基计划、综合评价、信息学相关专业面试、项目答辩和生涯探索，训练学生的逻辑表达、项目说明、问题分析和专业认知。

### 1.3 学生类型

系统只保留两类主学习模式。

#### A. 零基础入门型

典型特征：

* 没有编程经验；
* 对计算机专业认知模糊；
* 数学或英语基础存在差异；
* 不熟悉开发环境；
* 容易因语法错误产生挫败感；
* 需要短周期成果反馈。

#### B. 有基础拔高型

典型特征：

* 学过 Python、C++、Scratch 或信息技术课程；
* 可以完成基础编程题；
* 可能参加过信息学活动、科创活动或项目实践；
* 需要提升算法、工程、项目表达或专业面试能力；
* 需要避免重复学习已掌握内容。

“有基础拔高”可进一步标记为：

* `course_advanced`：校内课程拔高；
* `project_advanced`：项目能力拔高；
* `algorithm_advanced`：算法与信息学能力拔高；
* `major_exploration`：高校专业探索；
* `interview_preparation`：高校面试与项目答辩准备。

# 2. 设计约束

## 2.1 高考主线优先

系统不得因编程学习明显干扰语文、数学、英语及选考科目的正常学习。

学习计划必须考虑：

* 学生所在年级；
* 学期阶段；
* 周测、月考、期中、期末和模拟考试；
* 每周可用时间；
* 高三冲刺期；
* 家长或教师设定的时间上限。

默认策略：

* 高一以兴趣探索和基础能力为主；
* 高二以项目应用和专业探索为主；
* 高三以低负荷保持、成果整理和面试准备为主；
* 考试密集期自动降低新知识比例。

## 2.2 未成年人保护

系统必须满足：

* 不收集与学习无关的敏感信息；
* 不进行人格、智力或前途的确定性判断；
* 不使用羞辱、排名刺激或焦虑营销；
* 不鼓励熬夜、长时间连续编程；
* 不引导学生绕过学校作业或考试规则；
* 家长和教师只能查看被授权的数据；
* 学生可查看能力判断依据并提出异议。

## 2.3 教学提示优先

默认不直接提供可提交的完整作业答案。

系统采用：

```text
理解题意
→ 明确输入输出
→ 识别前置知识
→ 给出方向提示
→ 提供步骤框架
→ 提供局部示例
→ 学生再次尝试
→ 复盘阶段展示参考方案
```

以下情况可以提供完整参考实现：

* 任务已经结束并进入复盘；
* 教师明确授权；
* 当前内容是非考核示例；
* 学生已经完成自己的方案，需要进行对比；
* 系统明确标记为“参考代码，不可直接提交”。

# 3. 多 Agent 总体架构

## 3.1 Agent 划分

| Agent                          | 主要职责                            |
| ------------------------------ | ------------------------------- |
| Student Orchestrator Agent     | 识别学生意图、读取学习状态、选择业务 Agent、控制提示等级 |
| Major & Career Modeling Agent  | 高校专业认知、职业方向映射、能力图谱、成长路线         |
| Project Learning Agent         | 项目选题、项目拆解、里程碑管理、任务验收和过程提示       |
| Code Tutor Agent               | 代码分析、错误定位、调试引导、代码规范和变式练习        |
| Interview & Presentation Agent | 高校面试、项目答辩、专业认知问答和多轮追问           |
| Growth Assessment Agent        | 学习证据处理、能力更新、成长报告和难度调整           |
| Knowledge Retrieval Agent      | 检索教材、知识卡、示例、题目、项目模板和专业资料        |
| Teacher Copilot Agent          | 班级分层、任务设计、批改摘要、风险提示和人工复核        |
| Safety & Policy Agent          | 未成年人保护、作业边界、内容安全和权限控制           |

## 3.2 统一调用原则

* Agent 负责教学决策；
* Tool 负责确定性计算；
* 每个 Tool 只完成一个明确子任务；
* Tool 不得隐式修改学生能力；
* 能力变化必须由学习证据触发；
* 低置信度判断转化为诊断任务；
* 高影响判断必须允许教师复核。

## 3.3 系统主链路

```text
学生目标
→ 学生画像初始化
→ 专业与能力方向识别
→ 基础诊断
→ 个性化路线
→ 练习或项目
→ 代码与任务反馈
→ 学习证据生成
→ 能力状态更新
→ 难度与节奏调整
→ 阶段复盘
```

## 4.2 能力节点 `SkillNode`

高中生能力图谱应包含五类节点。

### 学科基础能力

* 数学逻辑；
* 函数与变量理解；
* 集合、排列组合和概率；
* 坐标、图像与数据关系；
* 英文技术词汇阅读；
* 信息提取和规范表达。

### 编程基础能力

* 变量与数据类型；
* 条件和循环；
* 函数；
* 列表、数组、字典、集合；
* 文件和数据处理；
* 调试；
* 模块化；
* 基础测试。

### 计算思维能力

* 问题分解；
* 模式识别；
* 抽象建模；
* 算法设计；
* 边界分析；
* 结果验证；
* 复杂问题分步表达。

### 项目能力

* 需求理解；
* 任务规划；
* 数据收集；
* 原型设计；
* 代码组织；
* 测试；
* 文档；
* 项目展示；
* 复盘。

### 专业探索能力

* 高校专业认知；
* 技术伦理；
* 人工智能基础认知；
* 数据与隐私意识；
* 项目陈述；
* 专业选择理由；
* 未来学习规划。

## 4.3 能力等级

采用六级能力模型：

| 等级     | 定义            |
| ------ | ------------- |
| L0 未接触 | 无有效学习或实践证据    |
| L1 能识别 | 能说出概念和基本用途    |
| L2 能模仿 | 能在示例或提示下完成    |
| L3 能独立 | 能独立完成典型问题     |
| L4 能分析 | 能排错、比较方案和解释原因 |
| L5 能迁移 | 能应用到新场景并讲解给他人 |

高中阶段通常以 L2 至 L4 为主要培养目标，不使用企业高级岗位标准要求学生达到不合理等级。

# 5. 模块一：专业与职业方向能力建模

## 5.1 模块定位

原“岗位能力建模”调整为“高校专业—职业方向能力建模”。

该模块不要求高中生直接选择具体岗位，而是完成以下递进关系：

```text
兴趣与学科优势
→ 高校专业方向
→ 大学阶段核心能力
→ 典型职业方向
→ 高中阶段可准备能力
```

例如：

```text
喜欢数学与逻辑
→ 计算机科学、人工智能、数据科学
→ 程序设计、算法、概率统计、数据分析
→ 软件开发、算法工程、数据分析等方向
→ 高中阶段学习 Python、算法基础和项目表达
```

## 5.2 子任务拆解

| 子任务      | 工具名称                          | 触发条件                 | 处理逻辑                 | 调用边界           |
| -------- | ----------------------------- | -------------------- | -------------------- | -------------- |
| 学生目标识别   | `direction.intent.resolve`    | 学生表达“想学编程”“想选计算机专业”等 | 提取兴趣、目标、年级和具体程度      | 不直接给出专业结论      |
| 专业方向映射   | `direction.major.map`         | 已获取兴趣和基础信息           | 映射计算机类、人工智能、数据科学等方向  | 不将兴趣测评等同于专业适合度 |
| 职业方向解释   | `direction.career.explain`    | 学生询问未来职业             | 用高中生可理解语言解释工作内容和能力要求 | 不承诺收入或就业结果     |
| 高中能力图谱构建 | `direction.skill_graph.build` | 确定一个或多个探索方向          | 从专业要求反推高中阶段准备能力      | 不直接使用成人岗位完整图谱  |
| 基础能力诊断   | `direction.baseline.assess`   | 新学生或方向变化             | 汇总问答、微任务和已有作品        | 不以单次考试成绩决定能力   |
| 能力缺口计算   | `direction.gap.assess`        | 已有目标图谱和诊断结果          | 比较高中阶段目标与当前能力        | 不要求提前掌握大学全部课程  |
| 成长路线生成   | `direction.roadmap.plan`      | 完成能力缺口分析             | 按年级、时间和考试安排生成阶段路线    | 不与高考主科学习冲突     |
| 路线局部调整   | `direction.roadmap.replan`    | 时间、目标或表现变化           | 保留已完成成果并调整剩余任务       | 不因一次失败重建整条路线   |

## 5.3 处理逻辑

### 5.3.1 专业方向映射

系统从四类证据进行映射：

1. 学生明确兴趣；
2. 学科基础与学习体验；
3. 编程或项目微任务表现；
4. 学生对典型专业场景的偏好。

返回结果应为探索建议，而不是确定性结论：

```json
{
  "recommended_directions": [
    {
      "direction_id": "computer_science",
      "match_score": 0.78,
      "evidence": [
        "逻辑推理任务表现较好",
        "对算法和程序运行机制兴趣较高"
      ],
      "uncertainties": [
        "尚无长期项目证据"
      ]
    }
  ]
}
```

不得输出：

> 你一定适合计算机专业。

应输出：

> 当前证据显示，你对逻辑推理和程序机制的兴趣较明显，可以优先体验计算机科学方向的基础任务，再通过项目表现继续验证。

### 5.3.2 基础能力诊断

零基础学生采用低门槛诊断：

* 图形或规则推理；
* 简单流程描述；
* 代码阅读；
* 修改一段短代码；
* 独立完成一个微任务；
* 解释自己的思路。

有基础学生采用挑战式诊断：

* 找出程序错误；
* 完成边界测试；
* 优化简单算法；
* 讲解已有项目；
* 处理一个开放问题。

### 5.3.3 成长路线规划

路线必须包含：

* 阶段目标；
* 每周时间；
* 学习内容；
* 练习任务；
* 项目产出；
* 阶段验收；
* 降载条件；
* 调整触发条件。

建议阶段：

1. 计算思维与编程体验；
2. 基础语法和问题求解；
3. 数据、算法或网页方向体验；
4. 小型跨学科项目；
5. 专业方向探索；
6. 项目展示和面试表达。

## 5.5 输入输出规范

必需输入：

* 年级和学期；
* 学习目标；
* 每周可用时间；
* 编程经历；
* 学科基础概况；
* 考试时间约束。

核心输出：

* 专业探索方向；
* 高中阶段能力图谱；
* 当前能力区间；
* 重点缺口；
* 分阶段成长路线；
* 调整触发条件。

禁止输出：

* 确定性专业适配判断；
* 就业和收入承诺；
* 不考虑年级和高考安排的高负荷路线；
* 用单次分数定义学生潜力。

# 6. 模块二：高中生项目实训拆解

## 6.1 模块定位

项目实训模块将真实问题转化为高中生能够完成的阶梯式项目。

项目目标不是模拟大型企业系统，而是培养：

* 问题发现；
* 信息整理；
* 数据处理；
* 程序设计；
* 测试验证；
* 项目表达；
* 跨学科迁移。

适合的项目方向包括：

* 学习时间记录与分析；
* 校园活动报名原型；
* 古诗词检索工具；
* 英语单词复习程序；
* 物理实验数据分析；
* 环境数据可视化；
* 简单网页；
* 图像分类体验；
* 个人知识库；
* 校园问题调查与数据报告。

## 6.2 子任务拆解

| 子任务     | 工具名称                             | 触发条件           | 处理逻辑                                     | 调用边界             |
| ------- | -------------------------------- | -------------- | ---------------------------------------- | ---------------- |
| 项目选题推荐  | `project.topic.recommend`        | 学生想做项目但没有方向    | 根据兴趣、年级、技能和时间推荐                          | 不推荐超出设备和时间条件的项目  |
| 项目需求标准化 | `project.brief.normalize`        | 学生提交项目想法       | 提取用户、目标、功能、数据和边界                         | 不直接扩展成大型系统       |
| 项目难度评估  | `project.complexity.estimate`    | 项目范围初步确定       | 评估新知识、步骤、依赖和开放性                          | 不仅按代码行数判断        |
| 技能映射    | `project.skill.map`              | 确定项目需求         | 映射编程、计算思维和表达技能                           | 每个核心任务最多聚焦三个主技能  |
| 里程碑拆解   | `project.milestone.decompose`    | 项目准备启动         | 生成可运行、可展示的阶段成果                           | 每个里程碑必须可验收       |
| 任务拆解    | `project.task.decompose`         | 里程碑已生成         | 拆成 20 至 90 分钟任务                          | 不生成过长、不可恢复任务     |
| 前置知识检查  | `project.prerequisite.check`     | 学生进入任务前        | 判断 ready、conditionally_ready 或 not_ready | 环境问题不得判断为能力不足    |
| 验收标准生成  | `project.acceptance.generate`    | 创建任务           | 生成可观察、可测试标准                              | 禁止使用“掌握”“熟悉”等模糊词 |
| 提示计划生成  | `project.hint_plan.build`        | 任务发布前          | 生成分级提示和检查问题                              | 默认不包含完整代码        |
| 下一步提示   | `project.hint.next`              | 学生主动求助或多次失败    | 返回最小必要提示                                 | 不因一句“不会”直接给答案    |
| 项目提交评审  | `project.submission.review`      | 学生提交代码、报告或展示材料 | 按验收标准评价                                  | 不只评价界面或代码长度      |
| 项目复盘    | `project.retrospective.generate` | 里程碑或项目完成       | 汇总问题、解决方式和能力证据                           | 必须保留学生自我复盘环节     |

## 6.3 项目拆解原则

### 6.3.1 里程碑结构

示例项目：学习时间记录与分析工具。

```text
M1：明确需要记录哪些学习数据
M2：完成命令行数据录入
M3：保存和读取历史记录
M4：计算各学科学习时长
M5：生成简单统计图或文本报告
M6：处理错误输入和缺失数据
M7：完成使用说明和项目展示
```

每个里程碑都必须产生一个可以演示的结果。

### 6.3.2 原子任务粒度

默认任务时长：

* 高一零基础：20 至 40 分钟；
* 高一或高二有基础：30 至 60 分钟；
* 综合项目任务：不超过 90 分钟；
* 超过 90 分钟的任务必须继续拆解。

任务必须包含：

```json

  "goal": "本次需要实现的结果",
  "estimated_minutes": 40,
  "required_skills": [],
  "deliverables": [],
  "acceptance_criteria": [],
  "hint_policy": "progressive",
  "reflection_questions": []
}
```

### 6.3.3 分级提示

| 等级 | 内容          |
| -- | ----------- |
| H0 | 帮学生重新理解任务   |
| H1 | 指出需要使用的知识方向 |
| H2 | 给检查清单和关键问题  |
| H3 | 给步骤框架或流程图   |
| H4 | 给局部示例或关键语句  |
| H5 | 复盘阶段提供参考实现  |

提示升级条件：

* 学生提交了新的尝试；
* 当前提示后没有有效进展；
* 连续错误属于同一根因；
* 教师授权升级；
* 项目已经进入复盘阶段。

# 7. 模块三：代码与技能练习辅导

## 7.1 模块定位

代码辅导模块负责帮助高中生形成正确的程序理解、调试和验证习惯。

支持语言可按学校和学习方向配置，首期建议：

* Python：零基础和数据项目；
* C++：算法和信息学方向；
* JavaScript：网页和交互项目；
* Scratch 或图形化编程：低门槛启蒙。

## 7.2 子任务拆解

| 子任务     | 工具名称                             | 触发条件           | 处理逻辑             | 调用边界           |
| ------- | -------------------------------- | -------------- | ---------------- | -------------- |
| 语言与环境识别 | `code.context.detect`            | 收到代码或项目        | 识别语言、版本和运行方式     | 不执行代码          |
| 语法解析    | `code.syntax.parse`              | 确定语言后          | 定位语法错误并尽量生成部分结构  | 不把所有错误都解释为知识缺失 |
| 静态检测    | `code.static.scan`               | 代码可解析          | 检测变量、类型、控制流和常见风险 | 不替代实际运行        |
| 安全沙箱运行  | `code.sandbox.run`               | 需要验证且获得授权      | 限制资源运行代码并采集结果    | 禁止外网和宿主访问      |
| 错误根因定位  | `code.error.localize`            | 出现多个错误         | 识别最可能根因及影响范围     | 不按日志顺序简单堆砌     |
| 题意思路拆解  | `code.problem.decompose`         | 学生不知道如何开始      | 提取输入、输出、规则、步骤和边界 | 不直接生成完整程序      |
| 下一步提示   | `code.hint.next`                 | 学生卡住或提交失败      | 给出下一项可执行动作       | 受提示等级控制        |
| 代码讲解    | `code.structure.explain`         | 学生看不懂代码        | 按模块、流程和数据变化解释    | 避免只逐行翻译        |
| 最佳实践讲解  | `code.practice.explain`          | 代码可运行但可读性或结构较差 | 区分必须修复和优化建议      | 不把个人风格作为硬规则    |
| 简单性能分析  | `code.performance.analyze`       | 数据规模较大或学生主动询问  | 分析复杂度和明显重复计算     | 无运行数据时声明为估计    |
| 测试用例生成  | `code.test.generate`             | 学生需要验证程序       | 生成正常、边界和异常用例     | 不直接代替学生思考      |
| 变式练习生成  | `code.exercise.variant.generate` | 需要巩固或验证迁移      | 保持目标技能并改变场景和条件   | 不只替换数字和变量名     |
| 错误模式归档  | `code.error_pattern.record`      | 同类错误重复出现       | 记录错误类型和补救建议      | 不贴负面标签         |

## 7.3 代码分析流程

```text
识别语言
→ 语法解析
→ 变量与控制流分析
→ 可选运行
→ 测试结果聚合
→ 根因排序
→ 教学提示
→ 学生修改
→ 再次验证
```

## 7.4 错误分类

### 语法错误

* 括号或引号缺失；
* 缩进错误；
* 标点使用错误；
* 关键字拼写错误。

### 逻辑错误

* 条件写反；
* 循环边界错误；
* 初始化错误；
* 更新顺序错误；
* 漏掉特殊情况。

### 数据错误

* 类型不匹配；
* 列表索引越界；
* 空数据；
* 文件格式不符合预期。

### 方法错误

* 没有明确输入输出；
* 盲目修改代码；
* 不看错误信息；
* 不写测试；
* 只验证一个样例。

# 8. 模块四：高校专业面试与项目答辩辅助

## 8.1 模块定位

原“招聘面试准备”调整为：

* 强基计划相关面试；
* 综合评价面试；
* 高校计算机类专业认知面试；
* 科创项目答辩；
* 信息技术作品展示；
* 校内综合素质活动陈述。

系统不模拟成人招聘中的薪资谈判、工作年限或复杂企业管理问题。

## 8.2 训练内容

### 专业认知

* 为什么对计算机或人工智能感兴趣；
* 对目标专业的理解；
* 高中阶段做过哪些探索；
* 如何看待人工智能的作用与边界；
* 未来希望学习哪些内容。

### 项目陈述

* 项目解决什么问题；
* 自己负责什么；
* 为什么选择该方案；
* 遇到了什么困难；
* 如何验证结果；
* 项目还能如何改进。

### 逻辑与场景题

* 如何将复杂问题拆解；
* 如何分析数据；
* 如何判断方案优劣；
* 条件变化后如何调整；
* 技术使用中的伦理和隐私问题。

### 基础技术问答

* 程序、算法和数据的基本概念；
* 简单代码阅读；
* 常见错误排查；
* 与学生项目直接相关的技术问题。

## 8.3 子任务拆解

# 9. 模块五：成长评估与动态调整

## 9.1 模块定位

成长评估模块将代码练习、项目任务、面试回答、知识问答和学习行为转化为能力证据，并动态调整：

* 后续任务难度；
* 每周任务量；
* 复习比例；
* 提示上限；
* 项目开放程度；
* 面试问题深度。

系统关注的是能力变化，而不是简单统计学习时长和完成数量。

## 9.2 子任务拆解

| 子任务    | 工具名称                                 | 触发条件           | 处理逻辑            | 调用边界         |
| ------ | ------------------------------------ | -------------- | --------------- | ------------ |
| 学习事件接收 | `assessment.event.ingest`            | 提交、提示、测验或面试结束  | 校验、去重和记录事件      | 不直接生成能力结论    |
| 证据标准化  | `assessment.evidence.normalize`      | 新事件进入评估流程      | 转换为统一证据结构       | 保留原始数据       |
| 任务质量评分 | `assessment.task_quality.score`      | 任务完成           | 评价正确性、独立性、思路和验证 | 完成不等于掌握      |
| 能力更新   | `assessment.mastery.update`          | 获得有效证据         | 更新能力分数和置信度      | 单次变化设置上限     |
| 稳定性分析  | `assessment.stability.analyze`       | 同一技能存在多次证据     | 判断偶然成功和稳定掌握     | 样本不足时不判断     |
| 提示依赖分析 | `assessment.hint_dependency.analyze` | 多次使用提示         | 分析是否逐步减少帮助      | 不把主动求助视为负面行为 |
| 成长曲线生成 | `assessment.curve.generate`          | 周报、月报或学生查询     | 生成能力、独立性和提示依赖趋势 | 标注置信区间       |
| 阶段复盘   | `assessment.review.generate`         | 阶段结束           | 汇总成果、问题和下一步     | 不只展示排名       |
| 难度调整   | `adaptation.difficulty.adjust`       | 连续成功或失败        | 调整任务条件、开放性和提示   | 不因一次异常大幅调整   |
| 节奏调整   | `adaptation.pace.adjust`             | 考试临近、进度偏差或负荷过高 | 调整每周任务量和新知识比例   | 高考主线优先       |
| 补救计划   | `adaptation.remediation.plan`        | 关键技能反复失败       | 区分概念、过程、调试和环境问题 | 不重复安排完全相同任务  |
| 风险检测   | `assessment.risk.detect`             | 中断、挫败或质量持续下降   | 识别负荷、环境和学习风险    | 不进行心理疾病诊断    |
| 路线重算触发 | `adaptation.roadmap.trigger`         | 达到调整阈值         | 提出局部重算建议        | 不自动删除学生作品    |

## 9.3 证据权重

能力更新应综合：

```text
证据权重 =
评分可靠度
× 任务难度
× 独立完成度
× 迁移程度
× 结果验证质量
× 新近程度
```

示例：

| 证据           | 权重        |
| ------------ | --------- |
| 独立完成新场景项目任务  | 高         |
| 能解释并修复自己的错误  | 高         |
| 在 H4 提示后完成原题 | 中低        |
| 单次选择题正确      | 低         |
| 复制代码但不能解释    | 接近零       |
| 因环境配置失败      | 不作为负向技能证据 |

## 9.4 动态调难策略

调难维度包括：

* 是否提供代码骨架；
* 任务步骤数量；
* 输入数据规模；
* 边界情况数量；
* 是否要求解释思路；
* 是否要求写测试；
* 是否加入跨学科场景；
* 提示等级上限；
* 任务开放程度。

默认目标成功率：

* 新知识引导任务：75% 至 85%；
* 独立练习：65% 至 80%；
* 挑战任务：45% 至 65%。

对于校内考核或能力认证任务，不应为了保持成功率而降低统一标准。

## 9.5 学习节奏调整

触发条件包括：

* 连续两周完成率低于 60%；
* 实际耗时持续高于预计耗时；
* 临近重要考试；
* 提示依赖持续增加；
* 学习中断；
* 学生或家长调整时间上限；
* 同一错误反复出现。

调整策略：

* 降低每周任务数量；
* 减少新知识；
* 增加复习；
* 缩短单次任务；
* 将开放项目改为结构化任务；
* 暂停非必要项目功能；
* 考试后再恢复原路线。

# 12. 零基础入门完整工作流

## 12.1 初始化

收集最少必要信息：

* 年级；
* 是否接触过编程；
* 每周可用时间；
* 兴趣方向；
* 使用设备；
* 当前是否临近考试；
* 希望完成的第一个成果。

调用：

```text
student.profile.initialize
→ direction.intent.resolve
→ direction.baseline.assess
```

## 12.2 低门槛诊断

诊断时间建议控制在 20 至 30 分钟，包括：

1. 一个规则推理题；
2. 一个流程排序题；
3. 一段短代码阅读；
4. 一个修改代码任务；
5. 一个简单解释题。

系统需区分：

* 完全未接触；
* 能理解但不会写；
* 语法困难；
* 逻辑困难；
* 环境操作困难；
* 表达困难。

## 12.3 第一阶段路线

第一阶段通常为 4 至 6 周：

```text
程序是什么
→ 输入与输出
→ 变量
→ 条件
→ 循环
→ 函数
→ 小作品
```

要求：

* 第一周产生可运行结果；
* 每个知识点尽快进入练习；
* 不连续安排大量语法讲解；
* 每周至少一次思路表达；
* 每两周至少一个小作品。

## 12.4 日常练习闭环

```text
任务发布
→ 题意拆解
→ 学生尝试
→ 静态检测
→ 根因定位
→ 分级提示
→ 再次尝试
→ 测试验证
→ 能力证据更新
```

## 12.5 首个项目

首个项目应满足：

* 代码规模小；
* 有明确输入输出；
* 与学生兴趣或学科相关；
* 能在两至四周内完成；
* 不依赖复杂环境；
* 可以展示和讲解。

## 12.6 阶段复盘

输出：

* 学会了什么；
* 可以独立完成什么；
* 哪些错误反复出现；
* 使用提示的变化；
* 作品成果；
* 下一阶段推荐方向。

# 13. 有基础拔高完整工作流

## 13.1 已有能力导入

输入来源：

* 学过的语言；
* 已完成题目；
* 项目代码；
* 信息技术课程成果；
* 科创作品；
* 信息学练习记录；
* 项目答辩材料。

调用：

```text
student.evidence.aggregate
→ code.static.scan
→ project.submission.review
→ direction.baseline.assess
```

不得按“学习时长”直接判断等级。

## 13.2 挑战式诊断

优先使用：

* 程序排错；
* 算法变式；
* 边界测试；
* 代码讲解；
* 项目方案说明；
* 小型开放任务。

若挑战任务失败，再定位具体前置知识，避免从最基础内容全部重学。

## 13.3 拔高路线

根据方向选择：

### 项目方向

```text
需求分析
→ 模块化
→ 数据存储
→ 测试
→ 界面或可视化
→ 文档
→ 项目展示
```

### 算法方向

```text
基础数据结构
→ 枚举与模拟
→ 排序和查找
→ 递归
→ 动态规划入门
→ 图与搜索基础
→ 复杂度分析
```

### 人工智能体验方向

```text
数据准备
→ 特征与标签
→ 简单模型体验
→ 训练与测试
→ 结果评价
→ 偏差与伦理
→ 小型应用
```

### 专业面试方向

```text
专业认知
→ 项目陈述
→ 技术基础
→ 逻辑场景题
→ 多轮追问
→ 面试复盘
```

## 13.4 动态调整

连续成功且提示依赖低：

* 减少代码骨架；
* 增加边界情况；
* 要求写测试；
* 增加方案比较；
* 增加项目表达。

连续失败：

* 定位失败类型；
* 插入补救任务；
* 缩短任务；
* 降低并行新知识数量；
* 检查环境和时间负荷。

# 14. 教师与家长辅助模式

## 14.1 教师端

教师可配置：

* 班级学习目标；
* 编程语言；
* 项目主题；
* 每周任务量；
* 提示等级上限；
* 是否允许参考代码；
* 自动评分权重；
* 人工验收节点；
* 成果展示要求。

教师端输出：

* 班级能力分布；
* 共性错误；
* 分层任务建议；
* 提示依赖较高学生；
* 项目进度风险；
* 需要集体讲解的知识点；
* 自动评分低置信度项目。

## 14.2 家长端

家长端只应展示：

* 学习计划完成概况；
* 作品成果；
* 时间投入；
* 当前是否负荷过高；
* 可操作的支持建议。

默认不展示：

* 详细代码错误；
* 学生之间的公开比较；
* 未经教师确认的能力标签；
* 专业适配结论；
* 容易制造焦虑的预测。

# 15. 非功能要求

## 15.1 性能

* 学习状态查询：P95 小于 500 毫秒；
* 单文件静态分析：P95 小于 3 秒；
* 下一步提示：P95 小于 5 秒；
* 单题回答评分：P95 小于 8 秒；
* 路线规划：P95 小于 10 秒；
* 报告生成可以异步执行，但不得阻塞当前学习操作。

## 15.2 代码沙箱安全

* CPU、内存和运行时间限制；
* 禁止访问宿主文件系统；
* 默认禁止网络访问；
* 禁止读取服务端密钥；
* 依赖包白名单；
* 运行后清理；
* 恶意代码检测；

# 18. 最终工程约束清单

1. 所有学生任务必须绑定能力节点。
2. 所有能力变化必须由学习证据触发。
3. 所有评分必须返回维度分和证据。
4. 所有提示必须记录提示等级。
5. 默认不得直接输出可提交的完整作业。
6. 所有路线必须考虑学生年级和考试阶段。
7. 高考学习冲突时优先降低编程学习负荷。
8. 环境错误不得作为负向能力证据。
9. 一次高分或失败不得导致能力大幅变化。
10. 不得使用成人企业岗位标准直接要求高中生。
11. 不得对学生专业适配、智力或前途作确定性判断。
12. 不得为学生编造项目、奖项或面试经历。
13. 所有代码执行必须进入隔离沙箱。
14. 所有低置信度结论必须转化为诊断或人工复核。
15. 教师人工覆盖必须保留原始结果和修改原因。
16. 家长端不得默认展示排名或负面能力标签。
17. 项目必须包含问题分析、代码、验证、文档和展示。
18. 动态调难不得降低统一考核标准。
19. 所有专业和职业信息必须标注内容版本。
20. 系统目标是帮助学生形成计算思维、项目能力和专业认知，而不是提前复制成人职业培训路径。
